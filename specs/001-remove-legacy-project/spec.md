# Спецификация: удаление legacy-проекта и стабилизация поддерживаемого приложения

**Ветка feature**: `001-remove-legacy-project`
**Создано**: 2026-04-30
**Статус**: Draft
**Входной запрос**: описание пользователя: "Удалить старый проект, привести новый проект к архитектурным рекомендациям и лучшим практикам, оценить применимость и необходимость DDD."

## Пользовательские сценарии и проверка *(обязательно)*

### Пользовательская история 1 - один поддерживаемый путь приложения (Priority: P1)

Как разработчик, я хочу видеть в CurveAnalyzer одно поддерживаемое приложение и
один поддерживаемый путь сборки, чтобы обычная разработка не блокировалась
устаревшим legacy-кодом.

**Почему этот приоритет**: пока это не выполнено, репозиторий дает противоречивые
сигналы о production-направлении, а основная solution может падать по причинам,
не связанным с поддерживаемым приложением.

**Независимая проверка**: разработчик может открыть репозиторий, найти
поддерживаемое приложение, выполнить документированную команду сборки и получить
успешный результат без обращения к старому корневому WPF-проекту.

**Сценарии приемки**:

1. **Given** в репозитории есть старый и новый код приложения, **When**
   открывается или собирается поддерживаемая solution, **Then** в поддерживаемом
   пути участвуют только новое приложение и нужные ему слои.
2. **Given** разработчику нужна WPF-точка входа, **When** он смотрит структуру
   проекта, **Then** production entry point указан один раз и без неоднозначности.
3. **Given** в старом корневом коде есть поведение, которого еще нет в новом
   приложении, **When** планируется миграция, **Then** это поведение либо
   переносится, либо явно объявляется вне scope, либо временно сохраняется как
   документированное migration evidence до удаления.

---

### Пользовательская история 2 - понятные архитектурные границы (Priority: P2)

Как maintainer, я хочу иметь понятные границы между UI, use cases, доменными
понятиями, persistence и доступом к MOEX, чтобы изменения не размазывали детали
UI или инфраструктуры по всей кодовой базе.

**Почему этот приоритет**: направление на слои уже выбрано правильно, но границы
еще смешаны. Миграция должна оставить новый проект проще для понимания, а не
только переложить файлы.

**Независимая проверка**: reviewer может посмотреть поддерживаемые проекты и
убедиться, что UI-специфичные детали не протекают в application/domain-логику,
а база и online-data доступ остаются за явными сервисными границами.

**Сценарии приемки**:

1. **Given** сценарию нужны исторические ZCYC-данные, **When** application-логика
   запрашивает данные, **Then** она использует application-facing contract, а не
   создает напрямую UI, chart, database или network-объекты.
2. **Given** WPF-приложение стартует, **When** собираются зависимости, **Then**
   composition явный и сгруппирован так, чтобы регистрации каждого слоя были
   легко обнаружимы.
3. **Given** синхронизация данных сообщает progress, **When** application-слой
   выполняет работу, **Then** progress отдается через UI-neutral механизм.

---

### Пользовательская история 3 - легкий DDD там, где он помогает (Priority: P3)

Как разработчик, который меняет поведение финансовых кривых, я хочу использовать
единый язык предметной области и явно моделировать реальные правила, чтобы
расчеты и синхронизация данных оставались понятными.

**Почему этот приоритет**: DDD полезен для именования и изоляции yield-curve
понятий, но полноценная enterprise-DDD структура добавит больше церемонии, чем
сейчас нужно приложению.

**Независимая проверка**: разработчик может до изменения поведения кривых,
периодов, спредов или истории определить bounded context, ключевые доменные
термины и принятые DDD-паттерны.

**Сценарии приемки**:

1. **Given** разработчик меняет spread или rate-history поведение, **When** он
   смотрит доменную модель, **Then** он находит именованные понятия для trading
   dates, periods, yield points, historical series и spread series.
2. **Given** reviewer видит новый aggregate, domain event, repository или
   factory, **When** он проверяет план, **Then** паттерн обоснован реальным
   инвариантом или проблемой связности.
3. **Given** feature завершена, **When** maintainers читают spec и plan, **Then**
   видно, какие DDD-идеи приняты, а какие намеренно отвергнуты как лишние.

---

### Пользовательская история 4 - гигиена репозитория и повторяемая проверка (Priority: P4)

Как maintainer, я хочу, чтобы поддерживаемый проект собирался без
machine-local-артефактов и checked-in runtime database-файлов, чтобы будущая
работа повторялась на другой машине.

**Почему этот приоритет**: архитектурный cleanup неполный, если чистая сборка все
еще зависит от локального DLL path, runtime-состояния базы или
недокументированных ручных шагов.

**Независимая проверка**: разработчик может выполнить документированные команды
проверки на чистом рабочем дереве и понять ожидаемые warnings или временные
ограничения.

**Сценарии приемки**:

1. **Given** поддерживаемое приложение ссылается на packages и assets, **When**
   выполняется restore, **Then** проект не требует developer-specific local
   binary path.
2. **Given** приложению нужны runtime data, **When** приложение стартует или
   запускаются тесты, **Then** database files создаются, мигрируются или
   seed-ятся через документированное поведение, а не требуются как source files.
3. **Given** для части миграции еще нет automated tests, **When** создается plan,
   **Then** он определяет, куда будут добавлены tests, или почему временно
   допустима manual validation.
4. **Given** supported projects переводятся на новую техническую базу, **When**
   выполняется restore/build, **Then** target frameworks и NuGet versions
   управляются единообразно и повторяемо.

### Граничные случаи

- В legacy-коде есть chart workflow или расчет, который еще не представлен в
  поддерживаемом приложении.
- Удаление checked-in database files скрывает sample data, нужные для ручной
  проверки графиков.
- Поддерживаемое приложение сейчас опирается на local binary или package,
  недоступный на другой машине.
- Chart packages продолжают выдавать compatibility warnings, хотя приложение
  собирается.
- `LiveCharts.Wpf` не имеет обычного обновления, поэтому "обновить все packages"
  требует либо отдельной chart migration, либо явного documented exception.
- В репозитории нет test-проектов, поэтому validation должна добавить
  сфокусированный test project или явно определить manual coverage для UI-only
  поведения.
- Старая root solution и новая supported solution расходятся по target framework
  или package versions.
- На машине разработчика нет нужного .NET 10 SDK, хотя repo закрепил SDK policy.

## Требования *(обязательно)*

### Функциональные требования

- **FR-001**: Репозиторий ДОЛЖЕН иметь один поддерживаемый WPF application path
  для обычной разработки.
- **FR-002**: Старый root-level application project ДОЛЖЕН быть удален из
  поддерживаемого build path до завершения миграции.
- **FR-003**: Основные пользовательские workflow ДОЛЖНЫ остаться доступны в
  поддерживаемом приложении: yield curve по дате, rate history по period и spread
  между periods.
- **FR-004**: Любое legacy-only поведение, найденное во время миграции, ДОЛЖНО
  быть перенесено, явно объявлено вне scope или временно сохранено с названным
  условием удаления.
- **FR-005**: Поддерживаемая application logic ДОЛЖНА быть отделена от WPF
  controls, chart rendering details, database implementation details и MOEX
  transport details.
- **FR-006**: Progress и завершение синхронизации данных ДОЛЖНЫ сообщаться через
  UI-neutral механизм.
- **FR-007**: Поддерживаемые проекты НЕ ДОЛЖНЫ требовать checked-in runtime
  database files для build или start.
- **FR-008**: Поддерживаемые проекты НЕ ДОЛЖНЫ зависеть от developer-specific
  local binary paths.
- **FR-009**: Новое или перенесенное доменное расчетное поведение ДОЛЖНО иметь
  automated tests, если plan не документирует временную причину manual
  validation.
- **FR-010**: Миграция ДОЛЖНА документировать выбранный уровень DDD и отвергнуть
  лишние DDD-паттерны, которые не защищают текущие доменные правила.
- **FR-011**: Поддерживаемые library projects ДОЛЖНЫ target `net10.0`, а
  поддерживаемый WPF project ДОЛЖЕН target `net10.0-windows` или явно
  документированный equivalent Windows-specific .NET 10 TFM.
- **FR-012**: Репозиторий ДОЛЖЕН закреплять .NET 10 SDK policy через
  `global.json` или эквивалентный документированный механизм.
- **FR-013**: NuGet package versions для supported projects ДОЛЖНЫ управляться
  централизованно через `Directory.Packages.props`; project-level
  `PackageReference` НЕ ДОЛЖЕН дублировать `Version`, кроме явно
  документированных исключений.
- **FR-014**: Все обновляемые NuGet dependencies supported projects ДОЛЖНЫ быть
  подняты до latest stable из configured package sources на момент реализации.
- **FR-015**: Необновляемые или compatibility-risk packages, например chart
  dependency, ДОЛЖНЫ иметь явное решение: заменить, временно оставить как
  documented exception или объявить blocker до удаления legacy.

### Ключевые сущности

- **Supported Application**: WPF-приложение, которое остается после миграции и
  получает всю будущую production-работу.
- **Legacy Application**: старый root-level app и связанные source folders,
  которые должны быть удалены или изолированы от поддерживаемого пути.
- **Yield Curve**: набор доходностей по trading date для доступных periods.
- **Trading Date**: рыночная дата, для которой curve data могут существовать
  online, исторически или отсутствовать.
- **Period**: tenor/duration кривой, используемый для выбора rate-history и
  spread inputs.
- **Yield Point**: значение для одного period на одну trading date.
- **Historical Series**: сохраненные yield points по trading dates.
- **Spread Series**: разница между двумя period series, выровненными по trading
  date.
- **Data Source**: historical local storage или online MOEX data, откуда
  предоставляется curve information.

## Критерии успеха *(обязательно)*

### Измеримые критерии

- **SC-001**: Поддерживаемая WPF solution успешно собирается в Release одной
  документированной командой.
- **SC-002**: Новый contributor может найти supported application entry point и
  validation command в файлах репозитория менее чем за пять минут.
- **SC-003**: Три основных workflow можно вручную продемонстрировать из
  поддерживаемого приложения после удаления legacy.
- **SC-004**: Ни один supported project не ссылается на legacy root-level
  application code, checked-in runtime database files или machine-local binary
  paths.
- **SC-005**: Не-UI доменные расчеты, затронутые миграцией, покрыты automated
  tests или временным documented manual validation exception.
- **SC-006**: Implementation plan содержит явный DDD decision record: какие
  domain concepts моделируются, какие DDD patterns используются, а какие
  намеренно не используются.
- **SC-007**: Supported build выполняется .NET 10 SDK, и в supported project
  files не остается `net8.0`/`net9.0` target frameworks.
- **SC-008**: `dotnet list CurveAnalyzer.sln package --outdated` не показывает
  обновляемых packages для supported projects, кроме явно принятого documented
  exception.
- **SC-009**: `dotnet list CurveAnalyzer.sln package --vulnerable` и
  `dotnet list CurveAnalyzer.sln package --deprecated` не выявляют
  незафиксированных проблем в supported projects.

## Допущения

- Приложение в `src` является целевым будущим production-приложением.
- Пользовательское поведение нужно сохранить, если legacy behavior не объявлено
  вне scope до реализации.
- Эта feature является миграцией и cleanup, а не запросом на новые chart
  capabilities.
- Можно добавить небольшой test project, если подходящего test project еще нет.
- Runtime database files считаются generated state или sample data, но не
  обязательными source artifacts.
- .NET 10 SDK доступен в среде разработки и может быть закреплен без отдельной
  установки внутри этой feature.
- DDD используется прагматично: сначала domain language и clear rules, тяжелые
  patterns только при реальной необходимости в плане.
